# 認証改修の使い捨て環境での実機受入確認

本番や実ユーザーの資格情報は使いません。自動検証の実績は PR 本文に記録し、この手順を実施したこととは区別します。OS・ブラウザー・認証器の種類と成功／失敗／未実施だけを記録し、秘密、復旧コード、token、ticket、credential、callback URL、HAR は共有しません。

## 設定と本人確認

1. 同じ合成アカウントで二つの個別セッションと、別アカウントのセッションを作ります。ログイン中端末の一覧・現在の表示・自分の別セッションだけの失効・現在セッションのサインアウトを確認します。失効されたクライアントに「ログインが無効にされました」と速やかに表示され、そのアカウントだけが端末からサインアウトし、別の保存済みアカウントが残ることを確認します。再読み込み・次回起動でも「問題が発生しました」の後に曖昧なトークンエラーが出る状態にならないことを確認します。資格情報の変更または個別失効で既に無効になったセッションからサインアウトしても、revokeFailed が出ず、そのアカウントだけが片付けられ、ほかのアカウントが残ることを確認します。
2. セッションごとのフォルダー見出しに最新 IP・ブラウザー名・メジャーバージョン・OS・最終利用時刻・有効／失効済みが表示され、現在のセッションが明示されることを確認します。展開するとセッションの生 UA と個別失効、そのセッションの user_ip に基づく IP 履歴（初回確認・最終確認）を確認でき、同じ IP でも別セッションは統合されず、紐付けのない過去の signin 履歴は下の従来の表に残ることを確認します。enableIpLogging が無効の間は IP 履歴が追加されず、最新 IP や履歴が空になる場合があります。
3. パスキー・セキュリティキーの削除、パスワード変更、認証アプリや多要素認証など従来から他セッションを失効させる設定の変更前に、ほかの端末のログインが無効になる案内があり、確認ダイアログがある操作ではその中にも案内されることを確認します。パスキー・セキュリティキーの登録には他セッション失効の警告が出ず、登録後も別セッションでログインを継続でき、既存のログイントークンが変わらないことを確認します。TOTP 未設定のままパスキーを登録します。登録完了と同時に MFA が有効になり、登録フロー内で認証アプリの設定時と同じように 5 個の復旧コードが表示されることを確認します。名前変更・一覧・所有する鍵の削除が本人確認を要求することも確認します。
4. 登録フローに表示された復旧コードを安全な場所に保存します。別の MFA 有効化操作や登録後の所有鍵の再確認なしに、パスワードと登録したパスキー／セキュリティキーでログインできることを、UP のみの追加要素と UV 対応鍵を区別して確認します。TOTP 設定済みの場合も登録直後から鍵を第二要素として使え、残っている復旧コードが置き換わらないことを確認します。
5. パスワードと TOTP／復旧コード／パスキーで共通の本人確認を行います。TOTP が先に選ばれ、同じセッションでは 5 分間繰り返し操作でき、操作で期限が延びず、別セッションは昇格しないことを確認します。
6. 各入力や native UI を中断し、復旧コードの表示を閉じます。画面離脱・KeepAlive 再表示・アカウント切替・二重クリック・別端末からの失効を含め、古い結果の送信や別アカウントのサインアウトが起きず、開いた秘密入力や表示コードが消えることを確認します。
7. パスワード、メール、ログイントークンの変更を共通本人確認で実施します。変更後のセッション失効、古いメール確認リンク・復旧リンクの拒否、他アカウントへの影響がないことを確認します。
8. 最後の追加要素を、MFA の明示的な無効化なしに削除できないことを確認します。復旧コードを同時に消費しても一回だけ成功し、別コードの並行消費で状態が巻き戻らないことを確認します。
9. 鍵登録で有効になったパスキー MFA とパスキー単独ログインを併用します。単独ログイン中も、パスワードログイン無効中も、複数の鍵を続けて追加登録でき、各登録で MFA が有効になり、復旧コードが表示されることを確認します。追加登録で既存セッションやログイントークンが無効化・再生成されず、単独ログイン設定も維持され、新旧どちらの鍵も直ちにログインと本人確認に使えることを確認します。パスキー単独ログインは discoverable credential と厳密な UV を確認してから有効化します。確認済み復旧メールがある場合だけパスワードログインを明示的に無効化でき、通常のパスワードログインが拒否され、最後のパスキーが削除できないことを確認します。使い捨てメールへの再設定は MFA を消さず、古いセッションを失効させます。
10. アカウント削除は確認後に要求し、受理後だけローカル資格情報を片付けます。キュー障害・DB rollback で削除 intent が成立しない場合は削除しないことを確認します。配信キュー投入と遠隔受信の実績は分けて記録します。

## ログインと発行する token

1. Conditional UI が使える secure context と未対応ブラウザーを分けて確認します。手動操作・TOTP フローへ移った後に古い autofill がログインを上書きしないことを確認します。
2. パスワード検証後のログイン途中状態で、TOTP／復旧コード／パスキーを切り替えます。パスワード再送がなく、初回の期限が延びず、別ブラウザー・古い nonce・再利用・途中の認証方針変更が拒否されることを確認します。
3. MiAuth／旧アプリ承認／OAuth の各同意画面で、現在アカウントの個別セッションの本人確認と明示同意を要求することを確認します。別の保存アカウントの token を暗黙に代用しないことを確認します。
4. 有効期限を明示して token を発行し、HTTP・WebSocket・MCP の待機接続・再生・遅延応答が期限後に利用できないことを確認します。既存の期限なし token の互換性、承認 code の一回交換、承認元セッション失効前後の競合、発行済み token とブラウザーログアウトの独立性を区別します。

PIN／生体認証、外付けキー、端末間 passkey、Conditional autofill の組合せで利用できないものは未実施として残します。合成署名・仮想認証器・mock の成功を物理端末の確認で代用しません。
