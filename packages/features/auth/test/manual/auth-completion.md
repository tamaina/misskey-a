# 認証改修の使い捨て環境での実機受入確認

本番や実ユーザーの資格情報は使いません。自動検証の実績は PR 本文に記録し、この手順を実施したこととは区別します。OS・ブラウザー・認証器の種類と成功／失敗／未実施だけを記録し、秘密、復旧コード、token、ticket、credential、callback URL、HAR は共有しません。

## 設定と本人確認

1. 同じ合成アカウントで二つの個別セッションと、別アカウントのセッションを作ります。ログイン中端末の一覧・現在の表示・自分の別セッションだけの失効・現在セッションのサインアウトを確認します。失効されたクライアントに「ログインが無効にされました」と速やかに表示され、そのアカウントだけが端末からサインアウトし、別の保存済みアカウントが残ることを確認します。別アカウントに切り替えた後、失効済みアカウントへ戻る操作でも、待機表示が閉じてから「ログインが無効にされました」が表示され、失効済みの保存トークンと詳細情報だけが消え、現在の有効なアカウントを維持したままログインし直せることを確認します。再読み込み・次回起動でも「問題が発生しました」の後に曖昧なトークンエラーが出る状態にならないことを確認します。資格情報の変更または個別失効で既に無効になったセッションからサインアウトしても、revokeFailedが出ず、そのアカウントだけが片付けられ、ほかのアカウントが残ることを確認します。
2. ログイン履歴が新しい順にページングされ、同じセッションのsigninは最新の1件だけがセッション管理MkFolderになり（ページをまたいでも重複しない）、見出しの解析UA・最新IP・最終利用・このデバイス／有効／失効、展開時の確認付き個別失効・生UA・user_ipの初回確認／最終確認を確認します。リンクなしでUAがある履歴は成功／失敗・IP・日時と生UAを表示する失効ボタンなしのMkFolder、UAがない履歴は展開できない通常行になること、展開内のIP履歴がIP・初回確認・最終確認の列を持つ表で表示されること、セッションに紐付かないtoken/API-keyのuser_ipがユーザーに表示されないことを確認します。signup直後や過去の記録などsigninとリンクしないセッションも、UAの有無にかかわらず独立したセッション管理MkFolderとしてページングされ、同じ確認付き失効とセッション別IP履歴を利用できることを確認します。見出しには最終UA・最終利用と取得できる最新IPを表示し、IPの記録がなければ「記録なし」と表示されることを確認します。「このセッションのIP履歴」など今回追加した日本語ラベルに英語との不要な空白がないことを確認します。同じIPでも別セッションは統合されず、enableIpLoggingが無効でuser_ipが空でも、見出しの最新IPに同じセッションの最新signinのログインIPが表示され、展開内に空のIP履歴見出しや初回確認／最終確認ラベルが出ないことを確認します。
3. パスキー・セキュリティキーの削除、パスワード変更、認証アプリや多要素認証など従来から他セッションを失効させる設定の変更前に、ほかの端末のログインが無効になる案内があり、確認ダイアログがある操作ではその中にも案内されることを確認します。パスキー・セキュリティキーの登録には他セッション失効の警告が出ず、登録後も別セッションでログインを継続でき、既存のログイントークンが変わらないことを確認します。TOTP未設定のままパスキーを登録します。登録完了と同時にMFAが有効になり、初回発行時は認証アプリの設定時と同じように5個の復旧コードがモーダルに表示されることを確認します。「セキュリティキー・パスキー」のMkFolderを開くと本人確認後に鍵一覧が表示され、各鍵が名前を見出し・最終利用を末尾に持つ入れ子のMkFolderになり、その中で名前変更・削除ができることを確認します。名前変更・一覧・所有する鍵の削除が本人確認を要求することも確認します。
4. 登録フローに表示された復旧コードを安全な場所に保存します。別のMFA有効化操作や登録後の所有鍵の再確認なしに、パスワードと登録したパスキー／セキュリティキーでログインできることを、UPのみの追加要素とUV対応鍵を区別して確認します。TOTP設定済みの場合も登録直後から鍵を第二要素として使え、残っている復旧コードが置き換わらず、既存コードが再表示されないことを確認します。モーダルを閉じた後は復旧コードの再表示ボタンがなく、APIでも既存コードを取得できないことを確認します。再生成では以前のコードが無効になり、新しいコードだけが一度モーダルに表示され、ログインと本人確認で一回ずつ消費できることを確認します。
5. パスワードとTOTP／復旧コード／パスキーで共通の本人確認を行います。確認方法がラジオ形式で選べ、確認とキャンセルが同じボタン列に並び、TOTPが先に選ばれ、同じセッションでは 5 分間繰り返し操作でき、操作で期限が延びず、別セッションは昇格しないことを確認します。
6. 各入力やnative UIを中断し、復旧コードの表示を閉じます。画面離脱・KeepAlive再表示・アカウント切替・二重クリック・別端末からの失効を含め、古い結果の送信や別アカウントのサインアウトが起きず、開いた秘密入力や表示コードが消えることを確認します。
7. パスワード、メール、ログイントークンの変更を共通本人確認で実施します。変更後のセッション失効、古いメール確認リンク・復旧リンクの拒否、他アカウントへの影響がないことを確認します。
8. 最後の追加要素を、MFAの明示的な無効化なしに削除できないことを確認します。復旧コードを同時に消費しても一回だけ成功し、別コードの並行消費で状態が巻き戻らないことを確認します。
9. 鍵登録で有効になったパスキー MFAとパスキー単独ログインを併用します。単独ログイン中も、パスワードログイン無効中も、複数の鍵を続けて追加登録でき、各登録でMFAが有効になり、復旧コードは新規発行時だけモーダルに表示されることを確認します。追加登録で既存セッションやログイントークンが無効化・再生成されず、単独ログイン設定も維持され、新旧どちらの鍵も直ちにログインと本人確認に使えることを確認します。パスキー単独ログインはdiscoverable credentialと厳密なUVを確認してから有効化します。有効化前の本人確認状態にかかわらず、有効化のパスキー確認が一度だけで済み、UVなし・別ユーザーの鍵・別セッションのticket・再利用・期限切れ・途中の認証設定変更では有効化できないことを確認します。無効化では共通本人確認後に追加のパスキー確認が出ないことを確認します。確認済み復旧メールがある場合だけパスワードログインを明示的に無効化でき、通常のパスワードログインが拒否され、最後のパスキーが削除できないことを確認します。使い捨てメールへの再設定はMFAを消さず、古いセッションを失効させます。
10. アカウント削除は確認後に要求し、受理後だけローカル資格情報を片付けます。キュー障害・DB rollbackで削除intentが成立しない場合は削除しないことを確認します。配信キュー投入と遠隔受信の実績は分けて記録します。

## ログインと発行する token

1. Conditional UI が使える secure context と未対応ブラウザーを分けて確認します。手動操作・TOTP フローへ移った後に古い autofill がログインを上書きしないことを確認します。
2. パスワード検証後のログイン途中状態で、TOTP／復旧コード／パスキーを切り替えます。パスワード再送がなく、初回の期限が延びず、別ブラウザー・古い nonce・再利用・途中の認証方針変更が拒否されることを確認します。
3. MiAuth／旧アプリ承認／OAuth の各同意画面で、現在アカウントの個別セッションの本人確認と明示同意を要求することを確認します。別の保存アカウントの token を暗黙に代用しないことを確認します。
4. 有効期限を明示して token を発行し、HTTP・WebSocket・MCP の待機接続・再生・遅延応答が期限後に利用できないことを確認します。既存の期限なし token の互換性、承認 code の一回交換、承認元セッション失効前後の競合、発行済み token とブラウザーログアウトの独立性を区別します。

PIN／生体認証、外付けキー、端末間 passkey、Conditional autofill の組合せで利用できないものは未実施として残します。合成署名・仮想認証器・mock の成功を物理端末の確認で代用しません。
